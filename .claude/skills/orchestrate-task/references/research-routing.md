# research-routing — 調査の入口契約 (情報源ルーティングの正本)

調査タスク (明示の「調べて」も開発途中の暗黙の調査も) が「どの面をどの順で探すか」を導く判断表と、完了時の網羅宣言、取りこぼしの記録契約、検索基盤の実需ゲートの正本。到達機構 (どう読むか) は `monomi` skill が持ち、本書は選定 (どこを探すか) だけを持つ — 両者は混ぜない。入口の配線は `orchestrate-task` skill の調査分岐が本書を指す。

## 1. 判断表 — 調査の種類から「まずここ」を導く

出力は探索の順序列であって全面の強制ではない。上の行から順に当たり、十分な確度が得られた面で止まってよい (止めた面から下は宣言で `skipped + 理由` になる)。

| 調査の種類 | まずここ | 次 | 補足 |
|---|---|---|---|
| 定義・一次値 (レジスタ・電気特性・規格・API 仕様) | `genten` (一次資料 KB、`genten-lookup` skill) | 公式 docs (Web) | 一次値を Web 検索から始めない |
| 過去の裁定・設計知見・運用の教訓 | `shiron` (蒸留知見 KB — `INDEX` → 該当ノート → `shiron:` 引用) | `docs/decisions.md` / Git history | 専用 skill は無い。この 1 行が参照手順の正本 |
| ドメイン実装の知見 (DSP 等) | ドメイン docs (project の `harness.toml::[kb]` 宣言、例: audio-dsp-docs → `dsp:` 引用) | `genten` | 宣言が無い領域はこの行を飛ばす (宣言の追加を検討) |
| コードの実体・現状の挙動 | `rg` / 読み取り探索エージェント (当該 repo) | 蔵 (kura 管理 repo 群) の横断 grep | 文書より実体を正とする |
| 生きた動向・リリース・一般 Web | 通常の Web 検索・取得 | `deep-research` (大型のみ) | 届かないときの代替到達は `monomi` の判断表に委ねる |
| 生きた人物・組織の現在の発信・世評 (歴史的事実は百科・論文の行へ) | X 面 = grok レーン、その他 SNS 面 = 公開読取 | — | 「X を見ない」は宣言なしには許されない。到達手段の選定は `monomi` の判断表に委ねる |
| 論文・学術 | DOI・学術メタデータ面 | `genten` (取り込み済みなら) | DOI があるなら直接。到達手段は `monomi` の判断表に委ねる |

修飾 2 軸:

- **鮮度**: 確定値 (仕様・過去の裁定) は静的 KB を先に。動く対象 (相場・リリース・世評) は Web / SNS を先に。
- **機密度**: 機密を含む調査は `r.jina.ai` 等の外部送信面を禁止し、ローカル面 (KB・コード・蔵) のみで構成する (外部送信規律の正本は `monomi` の該当節)。
- **Grok web の明示許可**: `tazuna orchestrate call` の Grok read-only role は web を既定無効にする。上表の live Web / X 面を Grok に割り当て、prompt と repository context に secret・顧客データ・private code が無いと確認できた場合だけ `--allow-web` を付ける。

## 2. `required` の導出と網羅宣言

- **導出規則** (再現可能な形): (1) 問いを判断表の行に照合し、該当した**全行**の「まずここ」列の面の**和集合**を `required` とする。「次」列は `required` に含めない (探索の推奨継続先であって義務ではない)。(2) 当該 project の `[kb]` 宣言のうち問いのドメインに一致するものは `required` に加える (一致しない宣言は候補に留める)。(3) 複合調査 (複数行該当) では行ごとの由来を宣言に併記する。導出の実施と最終決定はその調査の統括 (単独調査では実行エージェント自身) が担い、レビュー時にレビュアーが導出の妥当性を点検する。
- **required を `skipped` にできる条件**: その面が問いに対して期待情報量を持たないと**明示的に宣言できる場合のみ** (例: 発表当日のベンダー新機能で KB に蓄積が原理的に無い)。理由は必須で、レビュー点検の対象 (入口で狭く定義して漏れを隠す経路を塞ぐ)。
- **宣言の時機**: 終了時の網羅宣言 1 本に統合する。開始時宣言は大型・高リスク調査 (P-C 相当以上) のみ。
- **様式** (正本は `templates/research-coverage-declaration.md`):

```
必須面 (required):     <導出結果の列挙>
探した面 (searched):   <面: 見つけたもの / 出典>
届かなかった面 (unavailable): <面: 理由 (認証・レート・停止など)>
飛ばした面 (skipped):  <面: 理由>
出典: <引用 ID (shiron:/genten:/dsp:) と URL の列挙>
```

- **努力スケーリング**: 単純な事実確認 = 単独 + 数回のツール呼び出し / 比較調査 = 小規模並列 / 横断調査 = 役割分割 (詳細は `orchestrate-task` の区分に従う)。

## 3. 昇格則と miss 記録の契約

- **昇格則**: 同じ取りこぼし (実在した資料に届かなかった) が 2 回出たら、本判断表または該当 KB の索引を更新する。
- **miss 記録は半自動**: 自発記帳に頼らない。生成契機は次の 2 つに固定する — (1) レビューの synthesis 時 (担当: その回のレビュアー、`review-synthesis` skill に配線済み)、(2) 再調査の開始時 (担当: 統括)。置き場は shiron の観測ノート **`shiron:meta/research-miss-log`** (固定 ID・実在) を本線とし、tazuna 機構側の欠陥だった場合のみ backlog に置く。
- **1 行様式**: `- YYYY-MM-DD 検索語「<語>」→ miss (<面>): <実在した資料> — 契機: <synthesis|再調査> / 担当: <役割>`

## 4. 検索基盤の実需ゲート — 作らない宣言

ベクトル検索・埋め込み・横断検索基盤は**作らない**。着手を検討するのは次の 3 条件が全て実測で成立したときだけ:

1. 実在資料を grep / 索引が取りこぼす率が閾値超 (miss 記録の集計)
2. 索引の読込量が予算超過 (genten の 150 行分割則が早期の兆候)
3. 取りこぼしが語彙的でなく意味的 (同義語の言い換えで解決しない)

蔵横断の内容検索 (`kura search` は現状 registry メタデータのみ) は、実需成立後に kura CLI の機能候補として個別評決する。

## 5. 効果測定

- **3 指標**: 該当 KB の未参照 / SNS 面の未確認 / 無言断念 — いずれも「調査を含む plan / PR のレビュー点検」で判定する。
- **算式**: 率 = 該当件数 ÷ 対象調査件数。判定はレビュー担当が行い synthesis に記録する。
- **基準**: 導入前後それぞれ直近 20 件の比較 (対照条件のない前後観測であり因果の証明ではない)。
- **初期判定閾値**: 導入後 20 件で 3 指標いずれも導入前基準値から半減していれば「効いた」、悪化していれば入口の再設計 (独立 router skill 案の再評決) を起票する。
- **導入前基準値 (2026-07-11 実測、遡及 n=11)**: 適格母集団 = 調査を主活動に含む完了事例 (tazuna の merge 済み PR 8 件 + shiron の非移設ノート 3 件、2026-06-20〜07-11。抽出定義・全判定表・判定の限界 3 点は `plans/active/research-entry-contract/reviews/baseline-20260711.md`、完了時に Git history へ)。実測値: (i) 該当 KB の未参照 = **5/11 (45.5%)** (部分重複の確度の取り方で 45〜56% の幅) / (ii) SNS 面の未確認 = **1/4 (25.0%)** (適用可能な分母 4) / (iii) 無言断念 = **0/11 (0%)** (成熟事例への選別効果による過小の懸念を記録済み)。n が 20 に満たない理由 (shiron の移設ノート 39 件の除外ほか) も同記録に固定。前向き計数は導入後のレビュー synthesis から開始し、20 件到達時に本行を再測する。
